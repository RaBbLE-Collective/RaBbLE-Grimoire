## 1. Purpose

A minimal driver for the one power management chip on the RaBbLE-Pocket board (Waveshare ESP32-S3 Touch AMOLED 1.75B). The chip is reached over I2C. The driver does five jobs and no more:

1. Turn on the facilities the firmware needs from the chip: battery detection, the battery-voltage ADC channel, the power-key timing, and either latching of power-key events or silence of all interrupts.
2. Report power-key edges and clicks. The PWR button of this board is wired only to the chip (no ESP32-S3 GPIO sees it), so the chip's interrupt-status latch is the firmware's only view of that key.
3. Report battery percentage, battery voltage, charging and external-power presence.
4. Switch off supply rails nothing on the board uses.
5. Cut all power (soft power-off), after which the PWR key boots the board again.

It owns no task, no timer and no allocation. It does not configure the charger, the supply voltages, the fuel gauge, the watchdog or any sleep/wake behaviour. It never creates or deletes the I2C bus; the bus belongs to the board support code.

### 2.3 Who uses what (all callers found by search over `firmware/components`, `firmware/main`, `firmware/bsp`, `firmware/test`)

The only direct caller is the board table file `firmware/bsp/bsp_waveshare_175b.c` (component `bsp`, whose `CMakeLists.txt` lists `rabble_axp2101` in `REQUIRES`). No file in `components/` or `main/` includes the header. The gadget code reaches the driver only through the board table's function pointers, so what the driver returns is relied on by those modules too.

| Symbol | Call site and what it relies on |
|---|---|
| `rabble_axp2101_init` | Board init, once, on the main/startup task, right after the board support layer has created the shared I2C bus (`bsp_i2c_init()` then `bsp_i2c_get_handle()`) and before the RTC and IMU drivers attach to the same bus. Arguments: that bus handle, `key_irqs = true`, `pwron = RABBLE_AXP2101_PWRON_128MS` (one short click must boot the board from the off state). A non-`ESP_OK` result is tolerated: the caller logs a warning "battery status disabled" and carries on without `keep_rails`. After that failure the other four functions are still reachable (the board table still points at `read_power`, `poll_key` and `power_off`) and must stay harmless (section 9). |
| `rabble_axp2101_keep_rails` | Board init, only when `init` returned `ESP_OK`. Arguments `(BIT(0), BIT(0))`: keep DCDC1 and ALDO1, switch the rest off. A non-`ESP_OK` result is logged as a warning and ignored. |
| `rabble_axp2101_poll_key` | Board's button poll function, which the input task calls every 10 ms; the board code calls this function on every second poll (so about every 20 ms) and ignores the other three flags: only `RABBLE_AXP2101_KEY_PRESS` and `RABBLE_AXP2101_KEY_RELEASE` are used (mapped to the auxiliary-key press and release events). The input task copes with a press and a release latched in the same call, so the driver must report both when both happened. `KEY_CLICK` and `KEY_LONG` are not used today but must work. |
| `rabble_axp2101_read_power` | Wrapped by the board's power-read function and called by the input task every few seconds (and less often while the screen sleeps). The caller copies the four fields into the gadget's own power record, and only if the return is `ESP_OK`; on error the caller keeps its previous record. The values drive: the battery icon text (`battery_pct < 0` means "no battery", the charging symbol is shown when `charging`), the "on battery" decision (`!usb && battery_pct >= 0`), the automatic power-off timer (asleep on battery), the battery logger (`battery_pct` and `battery_mv` as start/now pairs) and the `status` console JSON. |
| `rabble_axp2101_power_off` | Installed directly as the board table's `power_off` hook. The input task calls it after a long press of PWR (3 s hold, "GOODBYE!" shown first), on a remote request, and after the automatic power-off timeout (asleep on battery past the power-off setting). Callers treat any return as "power-off failed": a successful power-off never returns to the caller because the chip cuts the CPU supply. After a return they wait 500 ms, log an error and show "COULDN'T POWER OFF". |

### 2.4 Threading, bus sharing, limits

| Item | Value |
|---|---|
| Tasks | `init` and `keep_rails`: startup task, before the input task exists. `poll_key`, `read_power`, `power_off`: the input task only, except that `read_power` may also be reached by any future caller. The driver must nevertheless be safe if any function is called from any task (see next row). |
| Locking | None of its own. Each register access is one complete I2C transaction through the ESP-IDF `i2c_master` API, which serialises transactions on the bus across tasks. Read-modify-write sequences are not atomic against other tasks that talk to this same chip; that is acceptable because the board has a single user task after startup. Never hold anything across a transaction. |
| Bus | The caller's `i2c_master_bus_handle_t`, shared with the RTC (address 0x51), IMU (0x6B), IO expander (0x20) and the audio codecs. The driver adds one device (7-bit address, `I2C_ADDR_BIT_LEN_7`, `scl_speed_hz` 400000) and never removes it, never deletes the bus, never reconfigures pins or clock. The device handle is kept in module-private state. |
| Transaction timeout | 50 ms per transaction. |
| Transactions | Single-register reads (write register address then read one byte, as one combined transaction) and single-register writes (address and value in one write). Do not rely on register auto-increment. |
| Blocking | Every function does a small, bounded number of I2C transactions (only what its rules in sections 4 to 8 require) and returns. Typical cost is under 1 ms per transaction at 400 kHz. None may spin, retry in a loop or sleep. |
| Stack | Negligible; no large locals. The input task has a small stack. |
| May call | ESP-IDF `i2c_master` API (`i2c_master_bus_add_device`, `i2c_master_transmit`, `i2c_master_transmit_receive`), `esp_log` and `esp_check`. Nothing else, and no other `rabble_*` module. |
| Memory | No heap allocation beyond what `i2c_master_bus_add_device` itself does. |

## 3. Register map used (datasheet section 6.13, "Register")

All registers are 8-bit; the chip's own reset defaults apply unless section 4 says otherwise. "RMW" means read the register, change only the named bits, write the whole byte back. Bits not named must be preserved by every write (including bits marked reserved or read-only), except where a register is write-1-to-clear, where section 5 says what to write.

| Reg | Datasheet name (section) | Fields the driver uses |
|---|---|---|
| 0x00 | PMU status1 (6.13.2.1, p. 25) | bit 5 VBUS good (1 = good); bit 3 battery present (1 = present). |
| 0x01 | PMU status2 (6.13.2.2, p. 26) | bits 6:5 battery current direction (01 = charge). |
| 0x10 | PMU common configuration (6.13.2.7, p. 26/27) | bit 0 Soft PWROFF (RWAC, write 1 to power off). Bit 1 (restart SoC) must never be set. |
| 0x27 | IRQLEVEL/OFFLEVEL/ONLEVEL setting (6.13.2.25, p. 28) | bits 3:2 OFFLEVEL (00 = 4 s, 01 = 6 s, 10 = 8 s, 11 = 10 s); bits 1:0 ONLEVEL (00 = 128 ms, 01 = 512 ms, 10 = 1 s, 11 = 2 s). Bits 5:4 IRQLEVEL are not touched. |
| 0x30 | ADC Channel enable control 0 (6.13.2.30, p. 31/32) | bit 0 battery voltage measure ADC channel enable. |
| 0x34 | vbat_h (6.13.2.31, p. 32) | bits 5:0 = vbat[13:8]. Bits 7:6 are the ch_dbg_en debug field: they are not data and are ignored on read. |
| 0x35 | vbat_l (6.13.2.32, p. 33) | bits 7:0 = vbat[7:0]. |
| 0x40, 0x41, 0x42 | IRQ Enable 0, 1, 2 (6.13.2.41 to 43, p. 34) | Section 5. In IRQ Enable 1 (0x41): bit 3 POWERON Short PRESS, bit 2 POWERON Long PRESS, bit 1 POWERON Negative Edge, bit 0 POWERON Positive Edge. |
| 0x48, 0x49, 0x4A | IRQ Status 0, 1, 2 (6.13.2.44 to 46, p. 35/36) | Write-1-to-clear (RW1C). In IRQ Status 1 (0x49) the same four POWERON bits 3, 2, 1, 0 as above. |
| 0x68 | Battery detection control (6.13.2.66, p. 39) | bit 0 battery detection enable. |
| 0x80 | DCDC ON/OFF and DVM control (6.13.2.69, p. 41) | bits 3:0 DCDC4..DCDC1 enable (bit 0 = DCDC1). Bit 4 see section 12 (ambiguity 2). Bits 7:5 are the CCM-mode and voltage ramp controls and must be preserved. |
| 0x90 | LDO ON/OFF control 0 (6.13.2.75, p. 42) | bit 0 aldo1, 1 aldo2, 2 aldo3, 3 aldo4, 4 bldo1, 5 bldo2, 6 cpusldo, 7 dldo1 enable. |
| 0x91 | LDO ON/OFF control 1 (6.13.2.76, p. 42) | bit 0 dldo2 enable. Bits 7:1 reserved, preserve. |
| 0xA4 | Battery percentage data (6.13.2.88, p. 45) | bits 7:0 battery percentage from the E-Gauge (section 6.11). |

The ADC data note in section 6.10 requires the high byte to be read before the low byte for a coherent 14-bit value.

## 4. Initialisation: required end states

After `rabble_axp2101_init` returns `ESP_OK`, the chip must be in the state of the table below. Where the table says "RMW" the other bits keep whatever the chip had. The implementer may order the accesses as it likes, subject to the three ordering notes under the table, and may skip a write if the register already holds the target (reads are cheap, writes are cheap; either is fine).

| # | Register and field | Required end state | Why the board needs it |
|---|---|---|---|
| E1 | Bus device at 0x34 on the caller's bus | attached, 400 kHz, 7-bit | The chip is on the shared I2C bus. |
| E2 | 0x27 bits 1:0 ONLEVEL | equals the `pwron` argument (enum value is the field value) | The power key is the only way to boot the board from the off state (automatic power-off, soft power-off). The firmware asks for 128 ms so one click wakes the gadget. Values above 3 are not valid enum values; mask the argument to two bits. |
| E3 | 0x27 bits 3:2 OFFLEVEL | 11b (10 s) | A held key must not trigger the hardware shutdown while the firmware is legitimately in a long push-to-talk hold (up to 8 s) or its own 3 s power-off gesture, but the hardware fallback must remain if the firmware hangs. |
| E4 (key_irqs true) | 0x41 bits 3:0 | all four set (RMW; other bits of 0x41 as the chip had them) | Makes the chip latch POWERON positive edge, negative edge, long press and short press in IRQ Status 1 (0x49). Positive and negative edge are disabled by the chip's reset default and must be enabled. |
| E5 (key_irqs true) | 0x49 bits 3:0 | clear (write 1 to those four bits) | No stale key event from before init may be reported by the first `poll_key`. No other bits of 0x49 are written. |
| E6 (key_irqs false) | 0x40, 0x41, 0x42 | all three equal 0x00 | Every interrupt source off. |
| E7 (key_irqs false) | 0x48, 0x49, 0x4A | all pending flags cleared (write 0xFF to each) | A pending, unserviced flag keeps the chip's open-drain IRQ output low against its pull-up (datasheet 6.12.1); an IRQ pin held low for more than 16 ms can also power the chip on again when customised that way (datasheet 6.5.4.2, item 4), which must not happen when nobody reads the flags. |
| E8 | 0x68 bit 0 | 1 (RMW) | Battery presence detection must be active so the battery-present flag in 0x00 and everything derived from it is valid. It is on at reset but is asserted explicitly in case it was changed. |
| E9 | 0x30 bit 0 | 1 (RMW) | The battery-voltage ADC channel must be running for 0x34/0x35 to hold a measurement. On at reset, asserted explicitly. No other ADC channel is touched (the other ADC channels stay as the chip has them). |

Ordering notes (the only ordering constraints):
- E4 must precede E5, and the clear must come after the enable (flags latched while enabling are discarded). E6 must precede E7 for the same reason.
- If the chip does not answer the first access of the bring-up, `init` stops and returns the I2C error; no register has been changed.
- A failed write at any step aborts and returns that error. Reads that exist only to produce a log line may fail silently.

Things `init` must not do: it must not change any rail enable or voltage, charger setting, current limit, fuel-gauge enable (0x18 stays at the chip's reset value, which has the gauge on), watchdog (0x19), sleep/wake (0x26), power-off source enables (0x22) or the BATFET. The board relies on the chip's factory (EFUSE) defaults for all of those.

Logging is the implementer's choice (at least one line on success is useful for D1); log text is the implementer's own.

If `init` is called with a NULL bus, return `ESP_ERR_INVALID_ARG`. Calling it a second time is not supported and need not be handled gracefully (it must not crash; an error return from the second device attach is acceptable).

## 5. Power-key events

The chip classifies the key itself (datasheet 6.5.4.1: long press, short press, negative edge, positive edge) and latches each in IRQ Status 1 (0x49) bits 2, 3, 1, 0. In this driver:

| Latched bit of 0x49 | Event flag returned |
|---|---|
| bit 1 POWERON Negative Edge (key went down) | `RABBLE_AXP2101_KEY_PRESS` |
| bit 0 POWERON Positive Edge (key went up) | `RABBLE_AXP2101_KEY_RELEASE` |
| bit 3 POWERON Short PRESS | `RABBLE_AXP2101_KEY_CLICK` |
| bit 2 POWERON Long PRESS | `RABBLE_AXP2101_KEY_LONG` |

Rules for `rabble_axp2101_poll_key`:

1. Read 0x49 and keep only bits 3:0. If the driver is not initialised (never attached), or the read fails, or no key bit is set: return 0 and write nothing.
2. Otherwise write 0x49 with exactly the observed key bits (write-1-to-clear), so that a key bit that latches between the read and the write is not lost, and so that other flags in 0x49 (battery insert/remove, VBUS insert/remove) are left alone. Never write 0xFF here.
3. Return the flags per the table. Several flags can be returned together. A failure of the clearing write is ignored (the event is still returned; at worst it is returned a second time on the next call).
4. Events are latched by the chip, not by the driver: the driver keeps no queue and no state between calls. Calls closer together than the caller's 20 ms rhythm, or farther apart, are both correct. A press and a release that both happened between two calls are returned together in one call.
5. With `key_irqs == false` at init, the key interrupts are off and `poll_key` always returns 0.
6. A short click normally latches negative edge, positive edge and short press, in that physical order, possibly all by the time of one poll. A hold past the chip's long-press time (IRQLEVEL, left at its reset value, nominally 1.5 s) latches long press while the key is still down.

## 6. Rail switch-off

`rabble_axp2101_keep_rails(dcdc, ldo)`: only the rails whose bit is set in the masks stay as they are; every other rail of the chip's rail set is switched off. A kept rail is not switched on if it was off.

| Mask | Bit to rail |
|---|---|
| `dcdc` bits 0 to 4 | DCDC1, DCDC2, DCDC3, DCDC4, DCDC5. Bits 5 to 7 of the argument are ignored. |
| `ldo` bits 0 to 7 | ALDO1, ALDO2, ALDO3, ALDO4, BLDO1, BLDO2, CPUSLDO, DLDO1. |
| `ldo` bit 8 | DLDO2. Bits 9 to 15 ignored. |

Rules:

1. The end state of each enable bit is (enable bit as it was) AND (bit in the mask). Registers 0x80, 0x90, 0x91 are the target (section 3); bits of those registers that are not rail enables (0x80 bits 7:5, 0x91 bits 7:1) keep their value. See ambiguity 2 for bit 4 of 0x80.
2. The three registers are read first; if any read fails nothing is written and the error is returned. Then the three are written; the first failing write aborts and its error is returned (rails already switched off stay off).
3. If the driver is not attached, return `ESP_ERR_INVALID_STATE` without any bus traffic.
4. Calling with masks that name every rail is a no-op in effect. Calling with 0 and 0 switches off everything, including DCDC1, which powers the ESP32-S3 itself and the board's 3.3 V rail: that would kill the system. This is the caller's responsibility; the driver does not guard (callers pass `(BIT(0), BIT(0))`).
5. Voltages are never touched.

Board requirement behind the only call made today (Waveshare ESP32-S3 Touch AMOLED 1.75B; DCDC1 output voltage register 0x82, ALDO1 register 0x92, set by the chip's factory defaults and by Waveshare's example at 3300 mV, see `examples/esp-idf/01_AXP2101/main/port_axp2101.cpp`):

| Rail | Net on the board | Voltage | Feeds | Kept? |
|---|---|---|---|---|
| DCDC1 | VCC3V3 | 3.3 V | ESP32-S3, flash, panel logic, I2C pull-ups and general 3.3 V loads | yes |
| ALDO1 | A3V3 | 3.3 V | analog supply of the audio codecs (ES8311 speaker codec and ES7210 microphone ADC) | yes |
| DCDC2, DCDC3, DCDC4, DCDC5, ALDO2, ALDO3, ALDO4, BLDO1, BLDO2, CPUSLDO, DLDO1, DLDO2 | not connected on the schematic, as established in the original project | n/a | nothing | no, switched off to save battery |

(Waveshare's example has commented-out lines that label DCDC3 as the ESP32-S3 core supply and BLDO2 as the microphone supply; those are leftovers of other board variants, and the project's device checklist in section 10 proves the current board does not need them.)

## 7. Power status

`rabble_axp2101_read_power(out)` produces the four fields. State table for the result:

| Input | Field | Rule |
|---|---|---|
| 0x00 bit 5 (VBUS good) | `usb` | true when set. Independent of whether a battery is present. |
| 0x00 bit 3 (battery present) | gates the three battery fields | When clear: `battery_pct = -1`, `battery_mv = 0`, `charging = false`. |
| 0x01 bits 6:5 (battery current direction) | `charging` | true only if the battery is present and the field equals 01b (charge). Standby (00b), discharge (10b) and reserved (11b) give false. (So "charge done" and "not charging" with the current flowing nowhere read false, which the UI relies on: the green charging symbol must disappear at full charge.) |
| 0xA4 (battery percentage) | `battery_pct` | If the battery is present, the read succeeds and the value is 0 to 100: that value. Any other case (read failed, value above 100): -1. |
| 0x34 bits 5:0 as the high part, 0x35 as the low part | `battery_mv` | If the battery is present and both reads succeed: (0x34 & 0x3F) << 8 | 0x35, in millivolts (1 mV per count, datasheet 6.10 Table 6-7). Otherwise 0. Read 0x34 before 0x35. |

Further rules:

1. Returns `ESP_OK` as long as the two status registers (0x00 and 0x01) could be read. A failed percentage read or voltage read does not fail the call; it degrades to -1 or 0 in the fields as in the table, and the caller will then show "no battery" for that sample. Do not substitute a stale value.
2. If either status register read fails: return that I2C error and leave `*out` completely unmodified. The caller depends on that (it keeps its previous record).
3. If the driver is not attached: return `ESP_ERR_INVALID_STATE`, `*out` unmodified.
4. `out == NULL`: return `ESP_ERR_INVALID_ARG` (callers never pass NULL).
5. Reads are done fresh each call; the driver caches nothing. Typical battery voltages run 3000 to 4400 mV; a reading above about 8191 cannot occur because of the 14-bit field.
6. Calling rate is about once every few seconds (and slower while the screen sleeps); the driver adds no rate limiting.

## 8. Soft power-off

`rabble_axp2101_power_off`:

1. If the driver is not attached: `ESP_ERR_INVALID_STATE`, no bus traffic.
2. Otherwise read 0x10 and write it back with bit 0 (Soft PWROFF) set and every other bit unchanged. Bit 1 (restart) must remain whatever it was, never set by this function.
3. Return the result of the write. Return the read error if the read failed, without writing.
4. On this board a successful write causes the chip to cut all supplies at once: the call normally never returns, or the CPU dies between the I2C acknowledge and the return. Both are expected. The driver adds no delay, no wait loop and no extra register writes; the caller owns the 500 ms wait and the failure message.
5. After the cut, pressing PWR for at least the ONLEVEL time set at init (128 ms) switches the board back on (datasheet 6.5.4.2, item 1).

## 9. Behaviour after a failed or skipped init

| Function | When the chip was never attached | When the device was attached but the chip is not answering |
|---|---|---|
| `init` | n/a | If the first register read fails, returns the error; later calls behave as in the right-hand column only if the attach had succeeded. |
| `keep_rails` | `ESP_ERR_INVALID_STATE` | the I2C error from the first failing read |
| `poll_key` | 0 | 0 |
| `read_power` | `ESP_ERR_INVALID_STATE` | the I2C error; `*out` unmodified |
| `power_off` | `ESP_ERR_INVALID_STATE` | the I2C error |

Neither state may hang, crash or spam the log at a rate that matters (the input task polls every 10 ms; do not log on the `poll_key` path at all except possibly once).

Run on the gadget with the new driver swapped in, serial console open (`>status`, `>power`).

| # | Action | Expected |

| D2 | Register dump with a bench tool or a temporary log: 0x80, 0x90, 0x91 | 0x80 bits 3:0 equal 0001b (and bit 4 = 0), 0x90 = 0x01, 0x91 bit 0 = 0. 0x27[3:0] = 1101b with the 128 ms setting (OFFLEVEL 11b, ONLEVEL 00b). 0x41[3:0] = 1111b. 0x68 bit 0 and 0x30 bit 0 are 1. |

| D5 | USB only, battery disconnected (or a board without battery) | `battery_pct` -1, `battery_mv` 0, `charging` false, `usb` true. |
| D6 | Click PWR once | One press and one release reach the input task (the board's auxiliary-key event log line shows both), no phantom repeats on the next polls. |

## 11. Test vehicle

A host test (no hardware) compiles the new `rabble_axp2101.c` against a stub of `driver/i2c_master.h` and `esp_err.h` (and a minimal `esp_log`/`esp_check` shim). The stub models a 256-byte register file behind `i2c_master_bus_add_device`, `i2c_master_transmit` and `i2c_master_transmit_receive`, with registers 0x48, 0x49, 0x4A behaving as write-1-to-clear and with a switch to make any transaction fail. Test cases:

1. `init` with `key_irqs` true and each of the four `pwron` values: after it, register 0x27 low nibble equals (11b << 2) | pwron, bits 7:4 unchanged; 0x41 bits 3:0 set with its other bits unchanged; 0x49 bits 3:0 clear; 0x68 bit 0 and 0x30 bit 0 set with other bits preserved; no write to any of 0x80, 0x90, 0x91, 0x10, 0x18.
2. `init` with `key_irqs` false: 0x40, 0x41, 0x42 = 0; pending flags in 0x48 to 0x4A cleared; `poll_key` returns 0 even if the stub then sets bit 1 of 0x49.
3. `init` against a stub whose first read fails: returns non-OK, no register changed.
4. `poll_key`: for every combination of the four key bits latched in 0x49 (and with extra non-key bits latched), the returned flags equal the table of section 5; the key bits are cleared; the non-key bits are untouched; a second call returns 0.
5. `read_power` matrix: battery present or absent, VBUS good or not, 0x01 bits 6:5 each of 00/01/10/11, percentage 0, 50, 100, 101, 255, voltage bytes with debug bits 7:6 set, read failures injected on 0xA4 only, on 0x34 only, on 0x00, on 0x01. Verify the table of section 7 and that `*out` is unmodified on status failure.
6. `keep_rails`: starting from several enable patterns, including all-on and every bit of 0x80 high bits; verify the AND rule, that bits 0x80[7:5] and 0x91[7:1] are preserved, that nothing is turned on, and that no write happens when a read fails. Call before init: `ESP_ERR_INVALID_STATE` and no transactions.
7. `power_off`: 0x10 gets bit 0 set and every other bit preserved, bit 1 never set; before init returns `ESP_ERR_INVALID_STATE`.
8. Before init and after a failed init: `poll_key` returns 0 and does not touch the bus.

An on-target build check (`idf.py build` for the gadget) and the checklist of section 10 finish the vehicle.

## 12. Ambiguities and decisions for the integrator

1. **Interrupt register numbering.** The datasheet calls the registers "IRQ Enable 0/1/2" (0x40/0x41/0x42) and "IRQ Status 0/1/2" (0x48/0x49/0x4A); older code often calls them 1/2/3. The power-key bits are in the register at 0x41 / 0x49, that is the datasheet's "IRQ Enable 1" and "IRQ Status 1". Addresses win over any name.
2. **DCDC5 and bit 4 of 0x80.** The interface (frozen) says bits 0 to 4 of the `dcdc` mask are DCDC1 to DCDC5. This datasheet edition's table for 0x80 labels bits 0 to 3 as DCDC1 to DCDC4 and gives no enable description for bit 4 (read-only, blank). Decision: apply the same AND rule to bit 4, as the interface states, because that matches the chip family (the AXP2101 has five DC-DC converters). Since the only caller keeps DCDC1 and the board has nothing on the others, the effect is "bit 4 is cleared if it was set"; if the write to a read-only bit has no effect, nothing is lost.
3. **Charging definition.** "Charging" follows the battery-current-direction field (0x01 bits 6:5) rather than the charger state machine field (0x01 bits 2:0). The two agree while charging and in standby; they can differ momentarily at state changes. The gadget's UI only needs "is current flowing into the battery". Do not change to the state-machine field without the integrator's approval, because the battery logger and icon colour use this boolean.
4. **Soft power-off with USB attached.** The datasheet lists VBUS rising as a possible power-on source "by customization" (6.5.4.2, item 2). It is not known whether this board's chip variant has it enabled. If the board restarts at once after power-off with USB attached, record it under the integrator's blockers; the driver must not try to cure it by writing registers not named here.
5. **Percentage right after a battery is inserted.** The E-Gauge (section 6.11) may report a low or zero value for a short time. The driver passes the register value through; the caller treats 0 to 100 as valid. Not handled further.
6. **Unused rails assumption.** The "unconnected" claim for DCDC2 to 5, ALDO2 to 4, BLDO1/2, CPUSLDO and DLDO1/2 comes from the original project and its schematic reading. Waveshare's example hints at a microphone rail on BLDO2 for another variant. D1 (microphone and speaker both working after boot) is the proof; if the microphone fails, report it to the integrator as behaviour and the call argument in the board file will be adjusted, not the driver.
7. **OFFLEVEL and datasheet field wording.** The field 0x27[3:2] is documented as OFFLEVEL (hold-to-power-off time) and 0x27[1:0] as ONLEVEL (hold-to-power-on time). Some text in the datasheet's 6.5.4.3 says the power-off by key also depends on 0x22 bit 1 ("PWRON > OFFLEVEL as POWEROFF Source enable"); its reset value comes from EFUSE. The original behaviour relies on that being enabled at the factory and does not write 0x22. Keep not writing it; D7/D8 tests the whole path only for the firmware gesture, so a bench check that a 10 s hold really cuts power is optional.
8. **Log output.** Not specified beyond section 4's last paragraph; tag text is the implementer's own.
